## 0. What a patch is

A patch is a **config diff**: a list of `replace` operations on JSON-pointer paths that
already exist in the agent config (`bench.heal.config.ConfigPatch`). The agent config is
the three values the Phase 3 critic snapshots (`services/critic/dev_adapter.current_config`):

| Key | Clean value | Under HALLUCINATION |
|---|---|---|
| `system_prompt` | `bench.agent._BASE_SYSTEM` | `bench.agent._GUESS_SYSTEM` (rewards guessing) |
| `MAX_STEPS` | 8 (a patch may set 1–30) | same |
| `TOOL_SPECS` | `bench.tools.TOOL_SPECS` | same |

Only HALLUCINATION lives in the config. The other four faults live in the tool backend
(`bench.tools.Toolbox`), which no patch can change. A Phase 3 proposal (whole-key
replacement, `_BASE_SYSTEM`/`_GUESS_SYSTEM` naming the system prompt) is converted by
`bench.heal.config.from_phase3`. A patch is applied to the failure's **deployed** config
(the faulted config above), and that patched config is used for every run of that patch:
own task, held-out tasks and regression tasks.

## 1b. When a task passes

- **Run pass (primary outcome):** the bench-v1.1 task checker passes: the agent stopped
  with a final answer, the answer matches gold by the v1.1 per-field rule, and every
  required tool ran without error (`bench.labeler.label_run(...).checker_pass`).
- **Task pass:** at least 2 of 3 runs pass. Runs are seeds 0, 1 and 2, at temperature 0,
  with cache tag `heal-s<seed>` in a fresh Phase 4 cache (`bench/heal/_state/`, not the
  Phase 1 cache). A no-patch run is therefore a real new sample, not a replay of the
  original trace.
- A provider error (`stop_reason = llm_error`) is retried up to 3 attempts in total. If
  it still fails, the run is recorded as `run_error` and counts as a fail. Run errors are
  reported.
- **Secondary outcome, reported but never gated:** "rule cleared". For faulted runs, the
  fault's own label rule did not fire. For regression runs it equals the primary outcome.
  It is computed from the same runs.

## 1c. The gate

A patch is promoted only if all three hold (`services.healer.gate.gate`):

1. the failing task now passes (task pass under the patch);
2. the held-out pass rate under the patch (share of its 5 held-out tasks that pass) is
   **strictly above** the no-patch rate on the same 5 tasks, with the same provider and fault;
3. no regression task goes from pass with no patch to fail with the patch.

## 1d. Experiments (H1–H6 as in the plan)

Each failure gets one patch per arm. Denominators count patches.

- **H1 repair rate:** share of patches that meet check 1.
- **H2 generalization rate:** share of patches that meet check 2. The mean held-out
  pass rate with and without the patch is also reported.
- **H3 regression rate:** share of patches with at least one regression break (check 3 fails).
- **H4 gate effect:** false promotions, gate vs the old rule.
  - *Old rule* ("same input improved"): promote if seed 0 of the failing task passes
    (the original trace failed). An old-rule false promotion is a patch the old rule
    promotes that fails check 2 or check 3.
  - *Gate:* on dev, a gate-promoted patch passes checks 2 and 3 by construction. So
    every gate-promoted patch is re-run on fresh seeds 3, 4 and 5 (own task, held-out,
    regression; the no-patch references stay at seeds 0–2). It is a false promotion if
    that confirmation fails check 2 or check 3.
- **H5 noise baseline:** the null patch (no change). Each failure, its held-out tasks and
  the regression set are re-run 3×. H5 = the share of failures whose own task passes with
  no patch. **Every gain is reported net of H5:**
  H1_net = H1(arm) − H1(H5) on the same failures, with the paired counts (fixed only
  with the patch / passed only without it). H2 is already measured against the no-patch
  rate. For the null patch itself, H2 and H3 are 0 by construction (it is its own
  reference), so seed-level noise is reported as well: the share of task cells whose 3
  seeds disagree, and how often seed 0 alone passes.
- **H6 judge bias:** Cohen's kappa between an LLM judge's pass/fail and the checker,
  over all evaluated runs. One judge is from the critic's model family and one from a
  different family. It is not run in this preparation step; its protocol (judge prompt,
  models, inputs) will be fixed in an amendment before the critic arms run.

Every rate is reported with counts and a 95% Clopper-Pearson interval, overall, per
fault and per provider, along with the spend (USD, LLM calls, wall time) per arm.

**Inapplicable patches.** A patch that cannot be expressed as a config diff (unknown
key, wrong type, out of bounds) is not run. It is listed with its reason, kept out of
the H1–H3 denominators, and counted in the arm's totals.

## 1e. Injection tag

Each patch is tagged deterministically against the clean config
(`bench.heal.config.injection_tag`). Look at every config path where the faulted config
differs from the clean one. Only `system_prompt` differs, and only under HALLUCINATION.
The patch is **`reverts_injection`** if, on such a path, the patched value equals the
clean value, or (for strings) no longer contains every injected segment verbatim.
Injected segments are the `insert`/`replace` spans of a `difflib.SequenceMatcher` diff
from the clean to the faulted string. Otherwise the patch is **`other_fix`**; the null
patch is `none`.

Results are reported separately for each tag, and **the headline uses `other_fix`**,
because reverting the injected prompt is an option no other fault offers.

## 1f. Arm selection and test

The critic arm used on test is the one with the **fewest false promotions on dev**
(gate false promotions, as defined in H4), ties broken by **higher H2**. Test is scored
once, at the end, with that arm only. The test failures, held-out sets and regression
set will be built by the same code and rules on the test split at that point.

*Known property of this rule, written down now:* an arm that promotes nothing has zero
false promotions, so on its own the rule favours conservative arms. The tie-break (H2)
only separates arms that tie. H1–H3 and gate promotions are reported for every arm, so
a "safe because inert" arm is visible.

## 1g. Expected gate failures (P20-style harmful patches)

A **P20-style patch** fixes its own task but breaks regression tasks:
check 1 passes, check 3 fails (`services.healer.gate.harmful_own_pass`). The gate must
reject these. Every one is counted and listed per arm. Named examples, expected before
any run:

- **"Use `id`, not `order_id`" for TOOL_MISFIRE** (a `TOOL_SPECS` description or
  system-prompt edit). Under the fault the backend takes only `id`, so the own task
  passes. With no fault, `get_order` rejects `id` alone ("missing required argument
  'order_id'"), so tool, plan and memory regression tasks break. A fix that tries
  `order_id` first and falls back to `id` would generalize without breaking anything.
- **Lowering `MAX_STEPS`** (e.g. to 2–3) for LOOP_DETECTED. It ends the loop early but
  truncates multi-step plan and memory tasks.
- **Task-specific instructions** that name the failing task's order id, company or
  answer. They can pass their own task without generalizing (check 2), and they can
  mislead other tasks (check 3).

## Expectations written before running

These are structural, from how the faults work. They are not predictions of numbers.

- **HALLUCINATION and LOOP_DETECTED own tasks cannot pass the checker under any config
  diff.** HALLUCINATION hides the target company's document from `search_docs`, so gold
  is unreachable except by a lucky guess. LOOP_DETECTED's `get_order` never returns the
  record. So reverting the guessing prompt is **not** an easy win under the primary
  outcome. It can only win on the secondary outcome (an abstention clears the
  hallucination rule).
- **22 of the 59 failures already passed the checker in their original trace** (11
  CONTEXT_BLEED, 11 PLAN_DRIFT): the label rule fired, but the answer was right. Their
  H5 rate is therefore expected to be high, and their H1 is only meaningful net of H5.
  CONTEXT_BLEED's rule fires on what the memory store returns, so no config diff can
  clear it.
- TOOL_MISFIRE (the backend rename) and the one checker-failing CONTEXT_BLEED are the
  failures where a config diff can plausibly fix the checker outcome.
- **Generic templates:** CONTEXT_BLEED (`memory_store`) and TOOL_MISFIRE
  (`tool_call_wrapper`) have no config key. Those 24 patches are inapplicable. The
  HALLUCINATION template tells the agent to abstain, which cannot pass the checker
  (it may clear the rule). `MAX_STEPS = 15` lengthens loops rather than ending them.

## Baseline arms run in this step

1. **H5 noise:** the null patch for all 59 failures.
2. **Generic:** the old fallback templates (`services/critic/fallback._FALLBACKS`),
   mapped to config diffs by a fixed rule (`bench/heal/generic.py`):
   - prompt templates are appended to the deployed system prompt;
   - the retry policy maps `max_steps` to `MAX_STEPS`, and its other fields have no key
     and are dropped;
   - the memory and tool-wrapper templates are inapplicable.

Outputs: `results/heal_runs.jsonl` (one record per run, with patch hash, intended and
applied config hashes, labels, cost and time), `results/heal_noise.json`,
`results/heal_generic_dev.json` and `reports/phase4/baselines_dev.md`.

## Harness guarantees

- **Run id:** `h4-<patch hash[:16]>-<base clean|guess>-<env fault>-<task>-<provider>-s<seed>`.
  It is a pure function of the experiment, so it is never reused for another one. A
  stored record with the same id and a different intended config hash stops the run
  (`RunIdCollision`).
- **Resumable and idempotent:** completed ids are skipped; identical runs requested by
  several failures execute once.
- **Applied-config check:** after every run, the hash of the config the agent actually
  used must equal the intended hash, or nothing is recorded (`ConfigMismatch`). That
  config is the system prompt sent with every LLM call, the step budget enforced and the
  tool list rendered.
- With the clean config and with the guessing config, `ConfiguredAgent` sends
  byte-identical LLM requests to the frozen `bench.agent.BenchAgent` (unit-tested).
